30. DEVELOPMENT, GITHUB, DATABASE AND DEPLOYMENT ARCHITECTURE

The application must be built using a clean, portable, Git-based production architecture.

SOURCE OF TRUTH

The GitHub repository must be the primary source of truth for the Banglar Darpan LIVE application.

Replit must work against the GitHub-connected project and maintain the complete application source code in Git.

Do not make Replit-only changes that are not reflected in the GitHub repository.

Every meaningful production change should be committed to GitHub.

Use a clear branch strategy, preferably:

main

for production.

Do not create unnecessary duplicate repositories.

Do not create unnecessary duplicate projects.

⸻

31. FREE-TIER-FIRST ARCHITECTURE

The initial production architecture MUST be designed to operate on free tiers wherever the providers’ current free tiers support the required functionality.

Priority:

1. Free tier
2. Open-source/native browser capabilities
3. Existing platform capabilities
4. Paid services only when genuinely required

Do NOT introduce a paid service merely because it is convenient.

Do NOT purchase a VPS, dedicated server, premium database, paid CDN, paid media server, or paid API unless technically necessary.

The initial target is:

$0/month infrastructure cost where the available free tiers are sufficient.

The application must still be designed so that individual services can be upgraded later without rebuilding the entire application.

⸻

33. DATABASE DECISION

Before implementing a database:

Evaluate whether the current application actually needs persistent backend data.

The initial Banglar Darpan LIVE application should remain as simple and inexpensive as possible.

For the current requirements:

* YouTube stream IDs can be stored as application configuration
* Promo dismissal can use localStorage
* static UI configuration does not require a database

Use Supabase or Firebase only where persistent server-side functionality genuinely requires it.

Potential future uses include:

* EPG data
* channel metadata
* viewer preferences
* broadcast schedules
* administrative configuration
* analytics
* authenticated management
* future CMS/API integration

Do not add unnecessary database complexity to the first production version.

⸻

34. SUPABASE / FIREBASE

If persistent backend functionality becomes necessary, evaluate:

Option A: Supabase

Use Supabase when PostgreSQL/database-oriented functionality is the better fit.

Potential uses:

* PostgreSQL
* EPG records
* channel configuration
* administrative data
* future authentication
* API access

Option B: Firebase

Use Firebase when its managed services provide a simpler fit for the application’s actual requirements.

Potential uses:

* authentication
* realtime data
* lightweight application state
* future analytics/integration

Choose the platform based on actual technical requirements.

Do not create unnecessary infrastructure.

The chosen service must initially remain within its available free tier where possible.

39. FREE-TIER COST CONTROL

The application must be designed with resource efficiency in mind.

Avoid:

* unnecessary database queries
* unnecessary server functions
* polling loops
* continuous background jobs
* unnecessary analytics
* multiple simultaneous YouTube players
* unnecessary third-party APIs
* unnecessary storage usage
* unnecessary image processing services

YouTube remains the actual video delivery platform for the supplied streams.

Do NOT build a separate video transcoding/CDN system.

Do NOT proxy YouTube video streams through our server.
